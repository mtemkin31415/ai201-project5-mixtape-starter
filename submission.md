# Mixtape — Codebase Map

Mixtape is a **JSON REST API** (no HTML frontend) for sharing songs with friends,
building collaborative playlists, rating songs, tracking listening streaks, and
viewing social feeds. It's built on Flask + Flask-SQLAlchemy with a SQLite database.

## Top-level files

| File | Responsibility |
|------|----------------|
| `app.py` | The application factory. `create_app()` configures the SQLite URI, initializes the shared `db` object, registers the four blueprints under their URL prefixes (`/songs`, `/playlists`, `/users`, `/feed`), and calls `db.create_all()`. `db = SQLAlchemy()` is defined here at module level so every other file imports it via `from app import db`. |
| `models.py` | All SQLAlchemy models and association tables (see below). |
| `seed_data.py` | Populates the DB with sample users, songs, tags, friendships, playlists, listening events, and ratings for local testing. |
| `requirements.txt` | Dependencies (Flask, Flask-SQLAlchemy). |
| `routes/` | HTTP layer — one blueprint per resource. |
| `services/` | Business-logic layer — all DB queries and domain rules live here. |
| `tests/` | Pytest suites for playlists, search, and streaks. |
| `instance/mixtape.db` | The SQLite database file (created at runtime). |

## The data model (`models.py`)

There are **6 entity models** and **3 association tables**. Every primary key is a
string UUID generated by `generate_uuid()` (a `uuid4()` wrapped as a string).

**Entities:**
- **`User`** — username, email, and the streak fields `listening_streak` +
  `last_listened_at`. Has relationships to shared songs, ratings, listening events,
  notifications, and playlists. Also has a self-referential many-to-many `friends`
  relationship (`lazy="dynamic"`).
- **`Song`** — title, artist, album, genre, plus social metadata: `shared_by`
  (FK to the User who shared it), `shared_at`, and a free-text `share_note`.
- **`Tag`** — a simple named label, attached to songs via a many-to-many table.
- **`ListeningEvent`** — one row per "user listened to song at time T". This is the
  raw event log that both streaks and the feeds are computed from.
- **`Rating`** — a user's 1–5 score for a song. A `UniqueConstraint(user_id, song_id)`
  enforces one rating per user per song, so re-rating updates the existing row rather
  than inserting a duplicate. (Note: ratings are their *own* model here — not stored
  on the Song directly.)
- **`Notification`** — `user_id` (recipient), a `notification_type` string, a
  human-readable `body`, and a `read` boolean.

**Association tables:**
- **`friendships`** — symmetric user↔user many-to-many.
- **`song_tags`** — song↔tag many-to-many.
- **`playlist_entries`** — the interesting one. It's a playlist↔song join table that
  carries **extra columns**: `position` (explicit ordering — songs have a defined
  place, not just insertion order), `added_by` (which user added the song), and
  `added_at`. Both `position` and `added_by` are `nullable=False`.

## Layering: routes → services

The app follows a strict **two-layer split**, and it's the clearest organizational
pattern in the codebase:

- **`routes/*.py`** do *only* HTTP concerns: read query params / JSON body, validate
  that required fields are present, call exactly one service function, and shape the
  response with `jsonify`. They translate a service's `ValueError` into a `400`
  (bad input) or `404` (not found).
- **`services/*.py`** hold *all* business logic and *all* database access. Services
  never touch `request` or `jsonify` — they take plain arguments, return models or
  dicts, and raise `ValueError` when something is missing or invalid.

Services are grouped by concern rather than by resource, so a single route file may
pull from several services:

| Service | What it owns |
|---------|--------------|
| `search_service.py` | `search_songs()` (case-insensitive `ilike` match on title **or** artist) and `get_song()`. |
| `notification_service.py` | `create_notification()` plus the two actions that *generate* notifications — `add_to_playlist()` and `rate_song()` — and the read side (`get_notifications`, `mark_as_read`). |
| `streak_service.py` | `record_listening_event()` and the consecutive-day streak math in `update_listening_streak()`. |
| `playlist_service.py` | Playlist creation and ordered song retrieval. |
| `feed_service.py` | `get_friends_listening_now()` (last 24h) and `get_activity_feed()` (most recent N, no time filter). |

Another consistent convention: models serialize themselves via a **`to_dict()`**
method, and services return `to_dict()` output (or lists of it) so routes can
`jsonify` directly without knowing the model shape.

## Data flow — adding a song to a playlist triggers a notification

This is the richest cross-layer flow in the app:

1. **`POST /playlists/<playlist_id>/songs`** hits `add_song()` in
   [routes/playlists.py](routes/playlists.py). The route pulls `song_id` and
   `added_by` from the JSON body and rejects the request with `400` if either is
   missing.
2. It calls **`add_to_playlist(playlist_id, song_id, added_by)`** in
   [services/notification_service.py](services/notification_service.py). Notably the
   playlist-mutation logic lives in the *notification* service, not the playlist
   service — because adding a song and notifying the sharer are treated as one action.
3. The service loads the `Song`, the adding `User`, and the `Playlist`, raising
   `ValueError` (→ `400`) if any is missing. It appends the song to the playlist via
   the `playlist.songs` relationship.
4. **The notification is the point of the flow:** if the person adding the song is
   *not* the person who originally shared it (`song.shared_by != added_by_user_id`),
   it calls `create_notification()` to insert a `Notification` row addressed to
   `song.shared_by`, with type `"song_added_to_playlist"` and a body like
   *"alice added your song 'Song Title' to the playlist 'Roadtrip'."*
5. The sharer later reads it via **`GET /users/<user_id>/notifications`**
   → `get_notifications()`, which returns their notifications newest-first.

The **rate-a-song** flow is the same shape: `POST /songs/<id>/rate` →
`rate_song()`, which validates the 1–5 score and upserts the `Rating` (updating the
existing row if the user already rated it).

The **listen** flow feeds the social features: `POST /songs/<id>/listen` →
`record_listening_event()` writes a `ListeningEvent` *and* updates the user's streak
in the same transaction. Those same events are what `feed_service` reads back to build
"friends listening now" and the activity feed.

## Patterns worth calling out

- **Blueprint-per-resource, prefix-mounted.** There is deliberately **no `/` route** —
  hitting the root returns 404 by design because this is a pure API.
- **UUID string PKs everywhere**, generated app-side, not DB auto-increment.
- **Events as source of truth.** Streaks and both feeds are *derived* from the
  `ListeningEvent` log rather than stored as denormalized counters (the one exception
  is `listening_streak`, which is cached on the User and updated on each listen).
- **`ValueError` as the universal "not found / bad input" signal**, caught uniformly
  at the route layer — services stay HTTP-agnostic.
- **Lazy-loading strategies are chosen per relationship:** `friends` uses
  `lazy="dynamic"` (so it can be queried/filtered), while `Song.tags` and
  `Playlist.songs` use `lazy="subquery"` for eager loading.
